从工作台进入的商家有三个具体问题：我接着做哪件商品？这一步会改到哪里？离开后去哪里找结果？建议用这三个问题决定首页内容、编辑器布局和结果状态，再统一视觉。

实测证据商品上新流程页面重构视觉与窄屏落地与验收

哪些地方真的妨碍工作

本次运行仓库内的联调工作台和商家后台。使用独立内存数据库、企业所有者和普通成员测试账号、项目自带商品照片，实际处理图片、修改表单、保存设置和授予项目访问权限。使用本机 Edge，桌面 1366 × 768、窄屏 390 × 844 与 320 × 700，坐标按 CSS 像素计。已有研究用来定位路径，再对照当前实现。尚未访谈真实商家，也没有线上频率或完成率数据；以下优先级按后果与可恢复性排序。

修改会悄悄消失

打开已保存的包款草稿，改标题，点侧栏「素材库」，再用浏览器后退。标题回到旧值，全程没有离开提示。已选主图的这份草稿，保存按钮顶部在页面约 1600px 处。用户为了看图需要离开，而保存状态和动作都远离当前输入。

一批图有两个结果，却只报一个“完成”

我同时处理正面主图和一张蒙版尺寸不匹配的图。第一张成功导出 800 × 800，第二张明确显示尺寸错误，顶部反馈却是「批次处理完成，结果已记录」。随后打开任务记录，页面显示「暂无记录」。素材仍然存在，用户缺的是重新找到这次批次、理解失败项并接着修的入口。

页面暗示可以并行编辑，保存行为只照顾一项

功能管理同时展开 6 份表单、18 个下拉框。把相邻两项的开放范围都改为「指定成员试用」，分别选择成员，只保存第一项。第一项保存成功，第二项随整页重绘回到「全企业」。项目侧授权本身可用，我也从「冬季上新」给测试成员林青成功授权，并在已授权名单看到她。

入口很多，却看不见正在做的商品

桌面侧栏有 22 个链接，首页「最近任务」标题在 705px。390px 宽时，页面标题在 488px，「最近任务」在 1663px。点「商品图片」有 15 个同名「详情」入口。走本地图片处理时，有素材的单项默认表单露出 8 个输入或选择控件，选好主图后工作区仍显示 0 张图片；无素材时需要另去素材库上传。

用一款商品串起首页、创作和交付

第一步 · 回来就认得手上的工作

首次打开，正文只问「要处理哪张商品图？」用户可以上传或从素材库选择。回访时把最近编辑的草稿放在最上方，露出缩略图、商品名、渠道、最近保存时间。多份草稿用几行可比较的列表；没有草稿就不显示空的继续区。余额和普通通知缩到顶栏，仅当额度或授权实际阻断当前操作时，在操作旁解释。

第二步 · 看着商品做决定

从草稿点「编辑主图」，立即显示这份草稿的当前主图，画布占主区约三分之二。右侧只问会影响当前结果的问题。切换为「保留完整图片」或「裁切填满」，画布立即显示差异；服务端生成期间保留原图。单张处理沿用文件名作为处理项默认名称。选择批量后才要求核对各项 SKU、数量和共同参数，避免熟练用户逐张重复输入。

第三步 · 看得懂结果，能交回原处

完成后同屏比较原图与结果。来自草稿时，主操作是「设为这份草稿的主图」，按钮旁显示草稿名；独立创作时提供下载、选择已有草稿或新建草稿。替换前可核对旧图和新图，确认保存后显示「已保存到工作台草稿」和返回入口。店铺写入另列接收店铺、变更字段与影响 SKU，在用户确认后执行。

批量结果页显示「已完成 1/2 · 1 张需处理」，成功行可交付，错误行说明「主体与蒙版尺寸不同」并给出更换蒙版的动作。回到任务页仍能按商品或批次找到两行结果。重试仅处理失败项；没有费用依据时不显示猜测的价格。

工程先决条件。现有生成结果可带入「新草稿」，本地批次成功项目前提供预览和下载。实现「回填原草稿」需要传递工作区、草稿 ID、主图素材 ID 和修订号，校验该草稿仍可写，再按版本保存。商品档案与渠道草稿若尚无可靠关联，先由用户选择目标。名称相同不足以自动关联。近期批次也需要可按权限列出的记录或索引。

每类页面采用适合这项工作的密度

用户所在位置首屏保留按需要展开
全局导航工作台、商品、创作、素材与资料、任务。顶部保留企业切换、通知、账户和有权限的管理入口。当前组的二级页面。店铺、客服、飞书和权利通知有清楚的「更多业务」入口；客服角色可直接进入会话。用找页测试验证命名和归属。
商品与草稿找商品用名称、缩略图、SKU 和状态；进详情默认看主图及当前渠道草稿。编辑时保留商品名、保存状态和保存按钮。规格、库存和渠道资料按工作分区，缺失项在交付检查时集中列出。新建、复用和删除退出常驻三栏，把删除放到明确命名的操作菜单。
任务与结果用「商品名＋动作」识别记录，显示时间、结果与可执行动作。失败和待确认能筛选，打开详情再返回保留位置。任务编号、模型、执行日志和技术错误码。用户先看到受影响项、原因和可恢复方式。
客服与经营客服默认面向待处理会话，选中后展示最近消息、接待身份和回复框。经营记录保留紧凑表格，数字列右对齐。新会话、引用文档、额外筛选和批量操作。只有已选行且后端支持时才出现批量按钮；返回列表保留筛选。
商家管理成员、项目和功能分别用摘要表。企业是否已启用、部署是否已配置是两列，管理员可以区分该找谁处理。点某行进入该项编辑。保存区写明企业、功能和作用范围，关闭回到原行。项目侧继续支持授权，成员侧补「可访问项目」。变更前核对对象，保存后原处回显。

怎样才看起来顺眼

现在首页的账户余额占了很大一块，但与「创作与经营」「最近任务」共用同样亮的边框、同样重的标题，里面的「查看」又都是按钮。人眼要把许多形状逐个读完才能判断轻重。建议把视觉重心留给商品、当前工作标题和一个主要动作。

  • 层级。工作页采用一块安静的底色和一层内容面。工作台以缩略图或编辑器画布为第一焦点。品牌冰蓝玻璃可留在导航选中态、主题控件和浮层，表单与表格使用稳定的实色背景。次要导航用有文字的链接；拒绝、撤销或停用提供对象名称和文字反馈。
  • 节奏。桌面先用页边 24–32px、跨组 24px、同组 8–12px 做样稿。标题 26–30px，正文 15–16px，辅助文字 13px。单个编辑字段以合适的栏宽呈现。库存、任务和成员表从 40–48px 行高起测，保留同屏比较的价值。以上为设计起点。
  • 窄屏。单行顶栏包含菜单、当前工作区和必要操作。图片编辑按「商品图、调整、结果」切换，同屏保留当前商品和主操作。草稿保存条随编辑可达，软键盘弹起后仍能看到当前字段及错误。表格只在自身区域横移；每行先露出可识别对象和状态。
  • 可读性。在冰蓝与浅色两套主题实测普通正文至少 4.5∶1 的对比度。状态同时用文字表示；用键盘完成选图、关抽屉、回到原行与保存，检验焦点可见、未被固定栏遮住。在 320 CSS px 核查适用的重排，在手机以约 44px 的主操作热区起测。W3C WCAG 2.2

想验证“顺眼”，可把新旧首屏各展示五秒后遮住，请使用者说出正在处理的商品、当前状态，以及会点哪里继续。另问哪一版更容易扫读、哪里太亮或太挤。前者检验视觉层级，后者收集主观偏好。

先交付一条完整路径，再推广

先修会造成返工的行为

草稿记录修改状态，站内跳转、浏览器返回和切企业之前处理未保存输入。保存失败保留原输入；版本冲突提供核对与恢复。后台改成单项编辑。批次显示成功／失败计数和失败项。用本报告的三个复现步骤做回归。

交付一条商品上新路径

从真实草稿列表做「继续编辑」；在编辑器内选素材；本地裁切；回填原草稿；刷新后核对商品、图片和修订。补批次记录的可找回入口。让已有单张、本地处理先可用，再接已配置的生成服务。

用结果决定推广范围

试用新首页、手机导航和图片编辑器，复测旧链接、无权限、空账户、失败及多草稿。达标后用相同的列表与单项编辑方式改商品、后台和经营页。客服角色单独验证常用入口的发现成本。

用真实工作检验能否上线

建议首轮找 5 名经常做商品内容的运营和 5 名管理过成员或项目的人，每组覆盖新手与熟手。同一人用不同商品或成员完成旧版和新版任务，交错先后顺序，不提示菜单名。以下是下一轮建议门槛；本轮没有真实用户测试数据。

给参与者的任务记录什么通过条件
用包的照片做一张方图，放回指定草稿首次点击、选图到预览的时间、独立完成、回读草稿 ID 与主图。至少 4/5 名运营独立完成；错商品或错草稿写入 0 次。记录耗时中位数，与同一任务的旧版比较。
接着改昨天的标题，中途找张图再回来找到目标耗时、是否回到原处、输入与保存状态。至少 4/5 名运营在 10 秒内从首页定位目标；未经确认丢失输入 0 次。
找出这次批量里失败的图，并继续处理能否说出成功与失败的数量、找回原批次、识别原因。至少 4/5 名运营独立找回失败项；已成功项重复处理或扣费 0 次。
让一位同事访问指定项目，核对影响范围目标企业、成员、项目与更改后的权限；返回后是否能定位原行。至少 4/5 名管理员独立完成；错授、扩大到全企业或静默丢弃第二项编辑 0 次。

桌面 1366 × 768 与手机 390 × 844 的首屏必须能看到主要对象和可执行的下一步。小样本用于发现和复测问题；记录每位参与者卡在哪一步，严重错误修正后再测。GOV.UK 主持式可用性测试
